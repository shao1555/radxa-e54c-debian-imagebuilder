# 07. Rockchip ベンダーカーネルとは何か・ディストリビューション選択への影響

## Rockchip ベンダーカーネル(BSP カーネル)とは

Rockchip が SoC ベンダーとして提供する **Linux カーネルのダウンストリームフォーク**のこと。
E54C で使われている `linux-6.1-stan-rkr4.1`(radxa/kernel のブランチ)を例にすると:

- **ベースは特定の LTS カーネル 1 バージョンに固定**される。ここでは 6.1 系(6.1.84)。
  前世代の SoC は 5.10 系(`linux-rockchip` / `linux-rk356x`)、さらに前は 4.19/4.4 系だった。
- その上に Rockchip が**数十万行規模の out-of-tree パッチ**を載せる。内容は
  ディスプレイ(VOP2/HDMI)、動画コーデック(MPP/rkvdec)、NPU(RKNPU)、2D エンジン(RGA)、
  DDR/devfreq、PCIe・USB・イーサネットの SoC 固有対応、電源管理など。
  メインラインにまだ入っていない(または永遠に入らない設計の)ドライバ群が中心。
- ブランチ名の読み方: `linux-6.1-stan-rkr4.1` = 6.1 ベース、`stan`(standard SDK)、
  `rkr4.1` = Rockchip SDK Release 4.1。Rockchip は SDK を「リリース版」として世代ごとに配布し
  (Radxa のパッケージ名 rk2410 = 2024-10 版 SDK 世代)、Radxa はそのフォークを保守する。
- **カーネルバージョンは上がらない**。6.1.84 に固定のまま、Rockchip/Radxa が必要な修正だけを
  バックポートする(upstream の 6.1.x stable を全部は追わない)。次にバージョンが上がるのは
  Rockchip が次の SDK 世代(例: 6.12 ベース等)を出したとき。

要するに「その SoC のフル機能を今すぐ使うための、ベンダー製の枝分かれカーネル」であり、
メインライン(kernel.org)にハードウェア対応が入るのを待たずに製品を出すための仕組み。

## 「互換性のあるディストロしか使えなくなるのか?」への答え

**厳密な意味では No、実用上の意味では半分 Yes** — 制約の正体を分解するとこうなる:

### 技術的には: カーネルとユーザーランドはかなり自由に組み合わせられる

Linux はカーネル⇔ユーザーランドの ABI(システムコール)を壊さない方針なので、
**古い(固定された)カーネル + 新しいディストロのユーザーランド**は基本的に動く。

- Debian bookworm の標準カーネルはそもそも 6.1 系なので、現状は完全に世代が一致している
- trixie など新しいリリースのユーザーランドも、glibc / systemd の最低カーネル要件
  (いずれも 6.1 より遥かに古いバージョンで満たされる)の観点では 6.1 ベンダーカーネルで動作可能
- 実際 rsdk の仕組み上、rootfs の suite とカーネル deb は独立しており、
  「trixie の rootfs に vendor 6.1 カーネルを入れる」ことは技術的に可能

### 実用上の制約は 3 つ

1. **Radxa がどの suite 向けにパッケージを作り、テストするか**(これが一番効く)
   - カーネル・U-Boot の deb は Radxa の APT リポジトリから来るため、
     Radxa がその suite 向けにリポジトリを用意しない限り「公式の組み合わせ」にならない
   - 現状: E54C は `products.json` 上 **bookworm / cli のみ**。
     trixie 向け APT リポジトリは既に稼働しているが、**rk2410 系カーネル/U-Boot の deb は
     まだ trixie に配信されていない**(2026-08 時点。詳細は [08-trixie-status.md](08-trixie-status.md))
   - rsdk 自体は trixie / sid / Ubuntu noble 等をサポートしており、対応 SoC 世代のボードでは
     trixie イメージが既に出ている。E54C が続くかは Radxa のパッケージング次第

2. **ベンダー専用ユーザーランドとの結合**
   - GPU(Mali blob)、動画(MPP)、NPU(RKNN)などのアクセラレーション用ユーザーランドは
     ベンダーカーネル固有の UAPI とペアで動くため、この部分だけは
     「ベンダーカーネル + Radxa が blob をビルドした suite」に縛られる
   - ただし **E54C はヘッドレスのネットワーク機器用途(cli イメージのみ)** なので、
     この制約の影響は実際にはほぼない。NIC・PCIe・USB が動けばよい用途では結合は薄い

3. **時間経過による摩耗**
   - ディストロが進むほど「新しいカーネル機能を前提にした新機能」(新しい BPF、io_uring、
     cgroup 機能など)が使えない場面が増える。多くは機能低下で済み、起動不能にはならない
   - 6.1 LTS 自体の upstream 保守は 2027 年末まで。それ以降はベンダー/Radxa の
     バックポート頼みになり、セキュリティ面の鮮度が落ちていく

### 出口: メインライン対応

この構造から抜ける唯一の道がメインライン化で、RK3588/RK3588S(RK3582 は RK3588S の
選別ダウングレード品)は Collabora 主導でメインライン対応がかなり進んでいる
(CPU、PCIe、GbE、USB、GPU=panthor など。動画コーデック等は途上)。

- Radxa もメインライン系パッケージ(`linux-stable` 6.1.68 / `linux-latest`)を持っており、
  一部ボードにはそこからメタパッケージを出している
- ただし **E54C 用の `linux-image-radxa-e54c` は現状 `linux-rk2410`(ベンダー 6.1)からのみ**
  提供されている(Radxa APT リポジトリの Packages 索引で確認済み)
- E54C のデバイスツリーが upstream に入った形跡もまだ見つからない(2026-08 時点。
  姉妹機 E24C の dt-bindings パッチは 2025-07 に LKML 投稿あり)
- 将来 E54C の DT がメインラインに入れば、Debian 公式カーネル(または Radxa の linux-latest)で
  動くようになり、ディストロ追従の制約は事実上消える。ルーター用途なら必要な機能が
  限られるため、自前で DT を用意してメインラインを動かす DIY の余地は比較的大きい

## まとめ

| 観点 | 制約の度合い |
|---|---|
| カーネル ABI 的に新しいディストロが動くか | ほぼ制約なし(6.1 で trixie userland は動く) |
| 公式サポートされる組み合わせ | **bookworm のみ**(Radxa のパッケージング・テスト範囲で決まる) |
| GPU/VPU/NPU アクセラレーション | ベンダーカーネル+blob に固定(E54C の用途では実質無関係) |
| 長期(bookworm EOL 後) | Radxa が trixie 対応 or メインライン対応を出すかに依存。監視ポイントは `products.json` の supported_suite と radxa-pkg の trixie 向けリリース |
