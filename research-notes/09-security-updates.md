# 09. ベンダーカーネルとセキュリティ更新 — 「誰が脆弱性対応を届けるのか」

「x64 と違って arm64 ではチップベンダーがバックポートしないと最新の脆弱性対応が難しいのか?」
という問いへの整理。結論: **概ね Yes。ただし本質は ISA(x86 vs arm64)ではなく、
「SoC 対応がメインラインカーネルに入っているかどうか」**。

## プラットフォーム別のセキュリティ供給モデル

| プラットフォーム | カーネルの出どころ | カーネル CVE 対応の担い手 |
|---|---|---|
| x86 PC / サーバー | ディストロ標準カーネル(メインライン系) | ディストロのセキュリティチーム(自動で届く) |
| arm64 サーバー(Graviton, Ampere 等) | ディストロ標準カーネル | 同上(x86 と同じモデル。Arm SystemReady の世界) |
| arm64 SBC / 組み込み(メインライン対応済みの SoC) | ディストロ標準 or メインライン系ベンダーパッケージ | ディストロ or ボードメーカー |
| **arm64 SBC(BSP カーネル依存)← E54C は今ここ** | **ベンダー BSP カーネル** | **チップベンダー + ボードメーカーのバックポート頼み** |

x86 では Intel/AMD が最初からメインラインで開発するため「ベンダーカーネル」がほぼ存在しない。
一方 SoC の世界では、対応がメインラインに入るまでの間、ベンダーフォークに縛られ、
その間は **Debian セキュリティチームの守備範囲外**(Debian が更新できるのは自分のカーネルだけ)になる。

## E54C の実態(2026-08 実測)

- upstream の 6.1.y stable は 2027 年末まで保守され、修正が毎週出ている
- しかし E54C のカーネルは **6.1.84 固定**(upstream の 6.1.84 リリースは 2024-04 頃)。
  upstream 6.1.y との差分は 2 年分以上蓄積
- Rockchip の stable 取り込みは **SDK 世代更新時のまとめ取り**方式:
  - rk2312 = 6.1.43 → rk2410 = 6.1.84 → rk2501 = 6.1.115 とベースが世代ごとに前進
  - 世代の途中ではベースは上がらない(必要な修正の個別バックポートのみ)
- Radxa の [linux-rk2410 changelog](https://github.com/radxa-pkg/linux-rk2410/blob/main/debian/changelog) 実測:
  - 6.1.84-5(2025-04)〜 6.1.84-8(2025-10)の内容は config 修正・submodule 更新が中心
  - **最終リリース 2025-10 以降、約 10 ヶ月更新なし**(2026-08 時点)
- Android には Google が ACK/GKI + 月例セキュリティボレティンでベンダーに適用を強制する
  仕組みがあるが、SBC の Linux にはその強制メカニズムがない(ベストエフォート)

## リスクの実際の大きさ

過大評価も禁物で、穴が開いているのは「カーネルと U-Boot/ファームウェア」だけ:

- **ユーザーランド(openssl, glibc, openssh, curl …)は通常の Debian セキュリティ更新がフルに効く**。
  公表される CVE の大半はこちら側
- カーネル CVE の多くはローカル権限昇格系。シングルユーザー運用のルーターで
  露出サービスを絞っていれば悪用経路は限られる
- ただし**ネットワークスタック系のリモート CVE は直撃しうる**。E54C のような境界デバイスでは
  ここが最大の懸念点
- U-Boot(2017.09 ベース)も同様に固定だが、攻撃面は物理アクセス前提が多い

## 実務上の対応策

1. **Radxa の APT リポジトリ経由のカーネル更新を確実に当てる**
   (`linux-image-radxa-e54c` の改版は apt 経由で届く。供給線はこれが唯一)
2. **Rockchip の次期 SDK 世代への移行を追う**(rk2501 = 6.1.115 系が既に他ボード向けに存在。
   E54C 向けに来れば stable 差分がまとめて縮む)
3. **露出面の最小化**: WAN 側に管理サービスを出さない、nftables で絞る、
   不要なカーネルモジュールのロードを避ける
4. **中長期はメインライン化を待つ/試す**: メインラインで動けば Debian 標準カーネル +
   security update という x86 と同じモデルに乗れる([07-vendor-kernel.md](07-vendor-kernel.md) 参照)。
   Rockchip はベンダーの中では upstream 対応が進んでいる部類(RK3588 系は Collabora 主導)

## まとめ

- 「ベンダーがバックポートしないと直せない」のは事実だが、それは arm64 一般の性質ではなく
  **BSP カーネル依存という状態**の性質。同じ arm64 でもサーバー機はx86 と同じモデルで回っている
- E54C は当面 BSP カーネル依存であり、カーネルのセキュリティ鮮度は
  Rockchip の SDK 世代更新 + Radxa のパッケージ改版のペース(実測: 数ヶ月〜年単位)で決まる
- ユーザーランドは Debian が守ってくれるので、「カーネルだけが別のセキュリティ供給線を持つ」
  と理解しておくのが正確
